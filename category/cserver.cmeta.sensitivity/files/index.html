1 Why labels

cMeta reads and writes whatever its machine holds - one interface over every repository plugged into it. That stays true for a shell, a script and everything that worked before. When a server lets people in - a website with users, an API, an MCP server, an agent's key - each person should get only part of it. A sensitivity label on a repository says how sensitive its information is; a person's clearance says up to which label they read.

The labels are the four of Microsoft 365, which most organisations use under these or similar words, plus personal:

  • No label = public. Labels are added repository by repository, where an organisation needs them; nothing changes for a repository that carries none. A server chooses another default for the unlabelled repositories it serves (default_sensitivity - general on a site of an organisation).
  • Ranked with personal without saying so: a word that is no label (a typing mistake hides, never shows), a repository of secrets (secrets: true), and the machine's own local repository - its logs, caches and settings. The engine's internal repository is public: the categories live there.
  • If unsure, the more protective label. Raising a label later is easy; information read by the wrong people cannot be taken back.

2 Labelling a repository and an artifact

A repository declares its label in its _cmr.yaml - every artifact in it carries that label:

alias: deals
uid: 4f0c2b9e1a7d4c3e
sensitivity: confidential

One artifact can raise its own label with sensitivity: in its _cmeta - one sensitive note in a general repository. It never lowers it:

sensitivity: highly-confidential
  • An edit of _cmr.yaml counts at the next call: no reindex, no restart.
  • The synonyms are read too: internal and private mean general, conf confidential, conf-high and restricted highly-confidential.
  • Reclassifying is moving the artifact to the repository of the right label (cx <category> move <artifact> <repository>:<artifact>). Through a door a move never lowers a label: lowering is a decision taken from a shell.
  • Never add sensitivity: public just to be explicit: a repository without a label is public already, and stays as it was for everyone.

3 The scope of a call

A server passes a few keys with every request it makes for a person - control keys of cm.access, and flags of every command:

keywhat it does
clearancethe highest label the call reads: public, general, confidential, highly-confidential, or personal - the server owner's, which reads everything
allow_reposrepositories read whatever their label: a grant by name (aliases, UIDs, patterns)
hide_reposrepositories never read, whatever the clearance or the grants
write_reposthe only repositories the call may write into; none: no write at all
default_sensitivitythe label of the repositories that declare none
 
r = cm.access({'category': 'note', 'command': 'find', 'arg1': '*',
               'clearance': 'general', 'allow_repos': 'deals',
               'write_repos': 'inbox', 'default_sensitivity': 'general'})
cx note find '*' --clearance=general --allow_repos=deals --write_repos=inbox
  • What is above the clearance is not found, listed, searched, drawn or read - by alias, by UID, by tag, by a page - and never written into.
  • The scope holds for every call the request makes. A nested call only narrows it: a wider clearance, a grant or a lower default asked again inside a cleared call count for nothing.
  • A shell passes none of the keys and sees what the machine holds: the scope is for the doors, the machine's own access control is for the machine.

4 People and their records

A server keeps a record per person and turns it into the keys with scope_for, for every request it makes for them - pages, API, MCP:

from cmeta.repos import scope_for

record = {'clearance': 'general',
          'repos': {'deals': 'read', 'inbox': 'write', 'drafts': 'none'}}

scope = scope_for(record, default_sensitivity='general')
# {'clearance': 'general', 'hide_repos': ['drafts'], 'allow_repos': ['deals', 'inbox'],
#  'write_repos': ['inbox'], 'default_sensitivity': 'general'}

r = cm.access(dict(request, **scope))
  • A record without a clearance reads general; one with no write grant writes nowhere.
  • The clearance personal is the server owner's: it reads everything on the server, every person's personal repositories included - give it to the owner alone. Another person reads a personal repository by a grant of that repository.
  • Take the scope from the record on the server, never from the request: a caller must not send its own clearance. A key never exceeds its owner - its own narrower scope is applied inside the owner's.
  • Name repositories by their UIDs in records: a denial by an alias that changed on a rename no longer denies.
  • What a person gets, every repository with its label, read, write and why: cx repo scope --clearance=general --allow_repos=deals --write_repos=inbox (cm.repos.scope_table(scope) from Python) - for administrators; a person sees their own rows (lesson 6).

5 Writes under a scope

whatthe rule
create, update, delete, move, copyonly into write_repos, never into a repository the call does not read - refused before anything is touched
a connection (--connect)a write on both sides (--ct: this side only); under a clearance written on the higher label's side only - the name of a confidential artifact never lands in a general one
move, copyunder a clearance never to a lower label; lowering is done from a shell
repositoriesa call with a write scope pulls, creates, unzips, unplugs and deletes none
the machine's settingsread by the code that serves a request (a config call made by code carries no scope keys and is not scoped); the request a server forwards for a person is
  • A scope is no sandbox. A repository that defines categories, tasks or pages holds code the server runs: a write grant there lets a person run code. Keep what people write through a door in repositories of data - an inbox.
  • A server's own bookkeeping inside a request - a cache built for every viewer, its state in local - goes between cm.repos.suspend_scope() and pop_scope(); a page that writes files itself asks cm.repos.write_refused(alias, uid) first.

7 Organising repositories

  • One repository per label and audience - general, confidential, highly-confidential; one per customer or topic where the audience differs. A label belongs to a repository; people belong to records.
  • One writing machine per repository. Curated repositories are written where they are curated; what people write through a server goes to an inbox repository written only on that server, curated and moved from there. Two-way syncs then never meet a file changed on both sides.
  • Git access must agree with the labels. A repository cloned to people's machines has a second access list - the git server's teams. Confidential and highly-confidential repositories can stay off git entirely and be reached through the server only.
  • A label is not encryption. Whoever has a shell on a machine reads its disk. Put a repository only on machines whose administrators may read it; keep a personal repository off shared servers unless that is acceptable.
  • Names are data too. The list of every repository with its label is for administrators; a person sees what they read.

A checklist for a server

  1. Label the repositories it serves; set its default_sensitivity.
  2. Keep a record per person: a clearance, grants by repository UID, write grants to inbox repositories.
  3. Pass scope_for(record, default_sensitivity=...) with every request - pages, API, MCP.
  4. The owner's personal clearance for the owner alone; administrators see the rights of everyone with cx repo scope.
  5. Check which repositories each machine holds.
